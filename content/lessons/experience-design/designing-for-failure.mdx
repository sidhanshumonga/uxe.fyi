Networks drop, servers time out and data arrives half-complete. Users on trains, in lifts and on cheap mobile plans see these states every day. Designing for failure means deciding what they should see and do when it happens.

## The failure list

For any screen, walk through:

- **Slow** — a request takes 5 or 10 seconds
- **Failed** — a request returns an error
- **Offline** — the connection drops mid-task
- **Partial** — some data loaded, some didn't
- **Stale** — the data shown is out of date

Each needs a design, even if the design is "show the cached version with a note".

## Keep the user's work

The worst failure is losing input. Save drafts locally, keep form values after an error, and queue changes made offline so they sync later. Saving in the background, and saying so quietly, removes the fear of losing work:

## Retry carefully

Retry transient failures automatically with increasing delays (exponential backoff) so you don't hammer a struggling server. Make retried actions idempotent, so that retrying a payment or a message can't do it twice. When automatic retries give up, offer a clear manual retry.

## Communicate calmly

Say what happened, what still works, and what will happen next: "You're offline. Changes will sync when you reconnect." Avoid alarming language for temporary problems, and don't block the whole screen for a failure in one part of it.
